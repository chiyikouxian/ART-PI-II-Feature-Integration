嵌入式大赛睿赛德赛道作品答辩稿
项目名称：基于 RT-Thread 与 ART-Pi2 的双手智能手语交互与边缘协同系统

一、30 秒开场

各位评委老师好。我们的作品面向听障人士与普通人之间的实时沟通场景，基于两块 ART-Pi2 构建双手可穿戴采集端，以 RT-Thread 作为端侧实时操作系统，采集双手 22 路姿态信息；通过 WiFi 将原始数据发送到 ROCK 边缘端完成识别，同时向 PC 端发送结构化数据，用于三维手部同步、设备监控和交互展示。右手还集成 INMP441 麦克风与语音转文字能力，左手集成 VTX316 语音播报能力。系统重点不是单一算法，而是通过 RT-Thread 的线程调度、设备抽象、同步机制和网络组件，将多传感器、无线通信、边缘推理、语音交互稳定地组织为一个实时系统。

二、项目背景与目标

1. 现实问题
手语交流存在信息壁垒。传统方案常常只做摄像头识别，受光照、遮挡和拍摄距离影响较大；单手手套又难以完整描述双手手语。

2. 我们的目标
（1）通过双手多 IMU 采集手部姿态；
（2）将原始高维时序数据交给 ROCK 边缘端识别，降低云端依赖；
（3）在 PC 端直观展示 3D 手部同步和翻译交互；
（4）加入语音输入与语音播报，形成“手语到文本/语音、语音到文本”的双向交互基础；
（5）保证多个外设和通信任务并发时系统仍可恢复、可观测、可演示。

三、总体架构

可以把系统概括为“四层、双链路、双手协同”。

1. 可穿戴端：两块 ART-Pi2
每只手配置 11 路 IMU：10 路 MPU6050 与 1 路 ICM-20948；通过两组 TCA9548A I2C 多路复用器扩展传感器通道。

左手侧重点：手部姿态采集、VTX316 语音播报、BLE/WiFi 通信。
右手侧重点：手部姿态采集、INMP441 数字麦克风、VAD 语音检测、语音转文字请求、BLE/WiFi 通信。

2. RT-Thread 实时控制层
RT-Thread 负责线程调度、I2C/SPI/UART/ADC/SAI 设备驱动接入、WLAN 与 lwIP 网络栈、信号量/互斥锁/事件等 IPC，同步管理传感器采集、网络重连、音频处理、按键和状态显示。

3. ROCK 边缘层
ROCK 在 9101 和 9102 端口分别接收左、右手原始 IMU CSV 数据，进行双手帧配对与边缘推理；同时部署 STT HTTP 代理，在 8080/stt 接收右手 PCM 语音数据，再通过 WebSocket/TLS 调用讯飞接口。

4. PC 可视化与管理层
Flask 后端提供设备数据管理、TCP 服务和 UDP 地址发现；Three.js 前端加载 GLB 手部骨骼模型，使用 Madgwick 姿态融合、关键帧校准、骨骼父链相对旋转和插值驱动模型；通道映射页支持按传感器配置左右手骨骼。

四、数据流说明

1. 手语/姿态链路
IMU -> I2C/TCA9548A -> RT-Thread 采集线程 -> 原始帧封装 -> WiFi TCP -> ROCK:9101/9102 -> 双手配对与识别 -> 控制/文本结果下行。

2. 可视化链路
IMU -> RT-Thread 数据处理 -> TCP JSON -> PC Flask:9109 -> REST 轮询 -> Madgwick/骨骼映射 -> Three.js 3D 模型。

3. 语音链路
INMP441 -> SAI + DMA -> 音频缓冲 -> VAD -> 16 位 PCM -> HTTP POST 到 ROCK:8080/stt -> 讯飞 WebSocket 识别 -> 文本结果。

4. 下行控制链路
ROCK/PC -> CMD:START、CMD:STOP、CMD:RESET_SEQ、MODE:MANUAL、MODE:AUTO、SAY:文本 -> ART-Pi2 操作模式状态机/左手语音播报。

五、RT-Thread 在项目中的核心价值

1. 为什么使用 RT-Thread
本项目外设多、并发任务多、对响应与稳定性有要求。裸机轮询会造成传感器读取、网络连接和音频录制互相阻塞；Linux 对单个低功耗可穿戴终端又偏重。RT-Thread 以较小资源占用提供抢占式调度、丰富组件和统一设备框架，适合 ART-Pi2 这类 MCU 端复杂物联网应用。

2. 线程划分
（1）IIC/OLED 初始化线程：完成 TCA9548A、OLED 等一次性初始化；
（2）IMU 采集线程：轮询 11 路传感器，完成陀螺仪静止零偏采样与原始数据更新；
（3）IMU WiFi 发送线程：约 90 ms 周期向 ROCK 发送原始 CSV，连接失败后退避重连；
（4）TCP 客户端线程：向 PC 发送 JSON 监控数据，独立于 ROCK 推理链路；
（5）网络管理线程：右手端独占 WiFi 连接流程，其他线程等待网络就绪，避免多个任务同时调用 WLAN 驱动；
（6）PC 地址发现线程：监听 UDP 9108，从广播报文获得 PC 的动态地址；
（7）音频采集/处理/语音助手线程：利用 SAI DMA 和信号量处理语音数据，避免网络请求阻塞采样；
（8）电池 ADC、按键、OLED/串口显示等低优先级任务。

3. 线程优先级设计原则
硬实时或数据完整性敏感的采集、DMA 事件处理优先；网络发送次之；UI、日志、电池显示放在较低优先级。这样即使网络短暂阻塞，也不会抢占 IMU 与音频采样的关键时序。

4. RT-Thread IPC 的使用
（1）互斥锁：I2C2 总线访问、音频处理上下文、TCP 端点更新等共享资源采用 mutex 保护，防止并发访问造成总线冲突或状态撕裂。
（2）信号量：SAI DMA 填充音频缓冲后释放信号量，音频处理线程被唤醒读取；这比不断轮询更省 CPU、更及时。
（3）事件：PC 地址发现和网络状态变化通过事件通知，网络任务不必忙等。
（4）消息/队列思想：模型参数和控制文本以有界缓存传递，避免网络接收线程直接操作业务状态。

5. 设备驱动框架与组件复用
项目使用 RT-Thread 的 I2C、UART、ADC、WLAN、Socket 抽象接口。上层业务关注“读取 IMU、发送网络帧、播放语音”，底层板卡与驱动差异由设备模型屏蔽，降低模块耦合度。

6. 网络栈与恢复策略
系统基于 RT-Thread WLAN 与 lwIP。网络管理线程完成连接，发送线程通过 ready 状态等待网络；TCP 失败后关闭旧 socket、延时重试；PC 地址通过 UDP 广播动态更新，避免更换场地后因 PC DHCP 地址变化而必须重刷固件。

六、关键技术与工程亮点

1. 双链路解耦
ROCK 原始数据链路服务于识别，PC JSON 链路服务于可视化和调试。两者独立重连，任一路异常不应让另一条链路完全失效。

2. 11 路 IMU 扩展
通过两组 TCA9548A 将同地址 MPU6050 分时接入 I2C，总共读取 10 路 MPU6050 和 1 路 ICM-20948。系统启动时扫描 WHO_AM_I 并输出每个通道状态，方便硬件排故。

3. 姿态融合与三维映射
前端使用 Madgwick 融合加速度计和陀螺仪；对异常数值做有限性和归一化保护；采用关键帧作为初始参考姿态，并通过“最近映射祖先”计算相对旋转，避免手掌姿态被重复叠加到手指关节上。

4. 双手帧配对与帧序号
WiFi 数据中包含时间戳、左右手标识和 frame sequence。ROCK 可据此配对两手时序帧，并在重连、复位时识别新会话，避免旧帧与新帧混合。

5. 语音端侧资源控制
INMP441 使用 SAI + DMA，录音缓冲限制为约 2 秒，语音活动检测只在达到最小语音帧数时发送，减少无效网络与内存占用。MCU 只发送 PCM，复杂 WebSocket/TLS 协议迁移至 ROCK，符合边缘协同分工。

七、演示流程建议

1. 先展示两块板连接同一 WiFi，OLED/串口显示网络、IMU、ROCK 状态；
2. 打开 PC 实时翻译页，进入页面后保持双手初始姿态约 3 秒，系统抓取关键参考帧；
3. 演示单指弯曲、手掌转动及双手动作，观察三维模型同步；
4. 展示 ROCK 端左右手 9101/9102 已连接及帧接收日志；
5. 对右手麦克风说一句固定短句，展示 STT 代理接收、识别文本和前端结果；
6. 可用控制指令展示开始/停止采集、模式切换或左手语音播报。

八、风险与诚实说明

1. 纯 6 轴姿态融合的航向角会长期漂移，磁力计/约束模型/周期性关键帧可进一步改善；
2. 拇指安装方向和骨骼局部坐标与其他手指不同，需要通过通道轴交换、符号翻转和安装四元数逐通道标定；
3. WiFi 地址会随场地 DHCP 改变，PC 已支持 UDP 发现；ROCK 地址与 STT 代理当前统一使用 ROCK_SERVER_IP，重新部署后只需修改这一地址并重新烧录；
4. 当前展示重点是可靠数据链路、实时交互和系统工程能力，识别精度需要通过更多真实双手样本持续训练与评估。

九、模拟问答

Q1：你们的核心创新是什么？
A：核心不是简单把传感器连上网络，而是把双手多 IMU 采集、RT-Thread 多线程实时控制、ROCK 边缘推理、PC 三维可视化和语音交互组成可恢复的端边协同闭环。我们特别将识别链路与可视化链路解耦，并通过会话、帧序号、重连和动态 PC 地址发现解决真实部署问题。

Q2：为什么选 RT-Thread，而不是裸机？
A：系统同时有 11 路 I2C 采集、WiFi TCP、BLE、按键、OLED、电池 ADC、右手音频 DMA 和语音网络请求。裸机超级循环很容易被网络或语音请求阻塞。RT-Thread 提供抢占调度、设备模型和 IPC，使采集、通信、UI 可以隔离运行。

Q3：为什么不直接在 ART-Pi2 上做完整 AI 推理？
A：多通道时序识别模型和语音 WebSocket/TLS 对 MCU 的算力、内存和开发成本要求较高。ART-Pi2 负责确定性采集、预处理和控制，ROCK 负责边缘模型推理和协议复杂度，既保持可穿戴端低时延，又能方便更新模型。

Q4：双手数据如何避免不同步？
A：每帧带时间戳、hand 标识和单调 frame sequence；ROCK 分别接收左右端口的数据后进行配对。断连重连时通过 HELLO/session 和序号复位识别新会话，避免将重连前后的数据误配。

Q5：多个 MPU6050 地址相同，如何挂在一条 I2C 上？
A：使用 TCA9548A I2C 多路复用器。读取某一传感器前先选中对应下游通道，再进行 I2C 事务。对共享的 I2C2 访问使用 RT-Thread mutex，保证没有两个线程同时切换复用器通道。

Q6：RT-Thread 的信号量在项目中解决了什么问题？
A：右手 INMP441 通过 SAI DMA 采集。DMA 完成一帧时释放信号量，音频处理线程阻塞等待该信号量后再取数据。这样没有数据时不占 CPU，有数据时又能及时处理，避免轮询造成的延迟和功耗。

Q7：为什么要有网络管理线程？
A：WiFi 驱动对重复并发连接较敏感。网络管理线程成为唯一的联网所有者，其他模块只等待 READY 状态。这样 TCP 客户端、ROCK 发送线程和地址发现线程不会同时竞争调用 WLAN 连接接口。

Q8：更换比赛场地、IP 改变怎么办？
A：PC 端通过 UDP 9108 广播自己的 TCP 服务端口，手套收到后运行时更新 PC 地址并触发重连。ROCK 同时承担 IMU 与 STT 服务，右手端把 STT 主机直接绑定为 ROCK_SERVER_IP，因此只需修改 ROCK 地址并重新烧录即可同步更新两个服务地址。

Q9：为什么三维模型需要关键帧校准？
A：传感器绝对安装角度和模型初始骨骼方向不一致。系统在演示开始后抓取当前姿态 Qref，后续使用 inverse(Qref) 乘 Qcurrent 得到相对旋转，只驱动相对于初始手势的变化，提升展示直观性。

Q10：为什么拇指容易与其他手指转向不同？
A：拇指的传感器安装面、关节运动平面和 GLB 骨骼局部轴都与四指不同。关键帧能消除零点，但无法自动改变旋转轴。因此要为拇指单独配置 axisSwap、flip 或安装四元数，再通过单轴动作测试验证方向。

Q11：Madgwick 算法为什么适合？
A：它计算量小，适合 MCU/浏览器实时运行，能融合陀螺仪的短时动态与加速度计的重力方向校正。我们同时加入 dt 钳位、四元数归一化、NaN 防护和零偏估计，避免长时间运行出现数值异常。

Q12：如果 WiFi 断开会怎样？
A：发送线程检测 connect/send 失败后关闭旧 socket，延迟约 3 秒重试；网络管理线程检测 WiFi 状态并重新连接。采集线程与本地状态机仍可运行，网络恢复后会重新建立会话。

Q13：如何证明系统不是“只跑通一次”？
A：我们为 TCP 会话字段、模板路由等增加了自动测试；前端包含 Madgwick 数值、骨骼父链和关键帧逻辑测试；串口提供 IMU 扫描、网络状态、会话和重连日志。答辩中可展示断网重连、端口连接和关键帧重置过程。

Q14：当前系统最大的局限是什么？
A：第一，姿态精度仍依赖传感器安装和通道标定；第二，6 轴融合的 yaw 长期漂移无法完全消除；第三，手语识别精度受训练样本规模影响。我们的处理方式是把硬件自检、运行日志、可调通道映射和边缘模型更新能力做扎实，为后续数据迭代建立工程基础。

Q15：下一步如何提升？
A：一是增加传感器安装标定流程和磁力计约束；二是建立统一的 ROCK 自动发现机制，取消固定 IP；三是扩展真实双手手语数据集并评估准确率、时延、丢包率；四是把模型版本、阈值和日志通过 PC 页面统一管理；五是优化语音链路的 VAD 阈值与离线兜底能力。

十、结语

我们的作品以 RT-Thread 为端侧实时基础，将“多传感器采集、无线通信、边缘识别、三维可视化、语音交互”从单个功能整合为可演示、可恢复、可扩展的双手智能交互系统。谢谢各位评委老师。
